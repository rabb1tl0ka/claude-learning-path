## Summary

**Routines.** A routine is a saved prompt plus the repo it works on and any connectors it needs, running on Anthropic's own managed infrastructure on a trigger (a cron schedule, an HTTP POST to an API endpoint, or a GitHub event like a new PR) — no self-hosted infrastructure or workflow file to maintain. Create one from claude.ai/code/routines or from inside Claude Code. Examples: a daily 9am dependency audit, a PR triager that fires on new pull requests. Caveats: routines are a research preview so behavior/limits will keep changing; a recurring schedule runs at most hourly; each run starts from a fresh clone of the default branch; and a run can only push to `claude/`-prefixed branches unless that's loosened per-repo — the guardrail against an autonomous run rewriting `main`.

**Headless mode and the agent SDK.** When a job needs your own environment or logic, drop to headless mode: `-p`/`--print` runs Claude Code as a one-shot command with no interactive TTY — reads stdin, writes stdout, pipes like any shell tool. `--bare` skips auto-discovery of hooks, skills, plugins, MCP servers, and CLAUDE.md, giving Claude plus only the tools explicitly allowed — faster startup and a consistent execution environment for CI (see [research/bare-flag-deterministic-mode.md](research/bare-flag-deterministic-mode.md) for what "deterministic" means here). Pair `--output-format json` with a JSON schema to constrain structured output; pull it with `jq` and pipe into a script or database. For multi-step automation, capture the session ID from JSON output and resume later with full context. The **agent SDK** embeds Claude Code inside a TypeScript/Python application: it exposes a `query` function with the same primitives as the CLI (prompt plus options like allowed tools, system prompt, permission mode), then you iterate the messages it streams back.

Rule of thumb: **routines** for repeat work you don't want to host; **headless mode** when the job needs your own pipeline; **`--bare`** when CI needs the same result every run; the **agent SDK** when the work belongs inside your own product.

**Automated PR reviews — two paths.**
1. **Managed Code Review** — an Anthropic-hosted service via the Claude GitHub App. An org admin enables it from the Claude Code admin settings, installs the GitHub app, and picks which repos it watches and when it runs (on PR open, on every push, or only when someone comments `@claude review`). A set of review agents analyzes the diff against the full codebase and posts findings as inline comments tagged by severity, with a summary table in the check run — deduplicated and ranked so you read a handful of real findings, not a wall of nitpicks. It never approves or blocks the PR; that judgment stays with a human. Currently a research preview for Team/Enterprise plans, and there's no managed autofix — findings only. Applying them is a local move: `/code-review` with its `--fix` flag applies findings to your working tree.
2. **Claude Code GitHub Action** — for jobs beyond review: implementing changes from a comment, scheduled reports, anything you'd otherwise write a workflow for. Set up via `/install-github-app` from inside Claude Code (needs repo admin) — walks through installing the GitHub app and setting the `ANTHROPIC_API_KEY` secret. The action itself is `anthropics/claude-code-action@v1`, with inputs: `anthropic_api_key` (required), `github_token` (defaults to `secrets.GITHUB_TOKEN`), `trigger_phrase` (defaults to `@claude`), `prompt`, and `claude_args` (a string of CLI args passed straight through, e.g. `--max-turns 5`, `--permission-mode dontAsk`, a scoped `--allowedTools` for a read-only report). A workflow file listening for `@claude` on PR/issue comments lets Claude push commits and post back what it did; cron triggers a daily rollup; `workflow_dispatch` allows a manual run from the Actions tab.

**Plugins.** A plugin packages a Claude Code setup — skills, sub-agents, hooks, MCP server configs — into one versioned, installable unit, so a team runs the same setup instead of copying `.claude/` folders between machines. Install with `/plugin install org/plugin-name` (session or team level); add a private marketplace once via `/plugin marketplace add org/claude-plugins` so later installs resolve through it with centralized discovery, version tracking, and updates. A plugin runs code with the installer's privileges and its hooks fire on every matching tool call whether or not you've read them — a community plugin's stop hook could silently call an external endpoint — so only install plugins/marketplaces from trusted sources, and inspect every hook, agent, and MCP server before enabling one. Plugins don't overwrite your configuration; they run alongside it: hooks stack (plugin's and yours both fire), and skills/agents/commands are namespaced under the plugin name so they can't clash. A plugin can ship a narrow `settings.json` slice — Claude Code only honors its `agent`/`sub-agent`/`statusline` keys — and setting `agent` promotes one of the plugin's sub-agents to the main thread with its own system prompt, tool restrictions, and model, which changes default behavior and is itself a reason to look before enabling. Building one: manifest at `.claude-plugin/plugin.json` (only `name` is required — it namespaces your skills as `plugin-name/skill-name`; version it like any dependency), with components discovered by directory convention mirroring the existing `.claude/` shape (one folder per skill, one markdown file per sub-agent, `hooks/hooks.json` and `mcp.json` at the plugin root).
