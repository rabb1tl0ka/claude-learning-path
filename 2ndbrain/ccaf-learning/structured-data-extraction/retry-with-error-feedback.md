## Summary

When an extraction fails validation (schema-level or semantic-level — see [semantic-vs-schema-validation.md](semantic-vs-schema-validation.md)), the naive fix is to just resend the same prompt and hope for a different result. This doesn't work reliably: if a prompt reliably produces an output that fails a given validation check, resending the identical prompt tends to reproduce the identical failure, burning retries and latency for no gain.

The effective pattern is **retry-with-error-feedback**: the retry request includes not just the original document, but also (a) the failed extraction attempt and (b) the *specific* validation error that occurred — not a generic "validation failed" message, but something like "line items sum to £450 but the stated total is £500" or "field `invoice_date` expected an ISO date, got the string 'unspecified'." Giving the model the precise, actionable diagnosis of what went wrong lets it actually self-correct, rather than guessing what might be different this time. This mirrors why good error messages in software (e.g. "expected int, got str" vs. "error") make debugging faster: specific feedback lets the next attempt target the actual failure.

But there's a hard boundary to this pattern that's easy to miss under exam pressure: **retries can only fix things the model *could* have gotten right given the information already available** — format mismatches, misplaced values, arithmetic/self-consistency errors, structural issues. They cannot conjure information that is genuinely absent from the source document. If a required field (say, a purchase order number) simply isn't printed anywhere on the invoice, no amount of retrying, no matter how detailed the error feedback, will produce a correct value — the model will either keep failing validation or (worse) start fabricating a plausible-looking value to satisfy the retry pressure.

A well-designed pipeline therefore needs a **detection step for this boundary case**: after some number of retries (or by directly checking whether the field appears anywhere in the source), the pipeline should recognize "this information is not present" as a distinct outcome from "extraction failed," and route it to a human reviewer or a flagged/missing-data status — not loop forever, and not accept a fabricated value just because it happens to pass schema validation.

## My Insights

Directly connects to two things: (1) multi-turn tool conversations from [multi-turn-conversations-with-tools.md](../../../claude-api/tool-use-with-claude/multi-turn-conversations-with-tools.md) (the retry loop is structurally the same "send result back, get corrected response" pattern as multi-turn tool use), and (2) the general prompt engineering principle of being specific rather than vague in instructions ([prompt-engineering-techniques.md](../../../claude-api/prompt-engineering-techniques/prompt-engineering-techniques.md)) — specific error feedback is that same principle applied to retries instead of the initial prompt. (Note: `tool_choice`/forced tool use is *not* actually covered in any `tool-use-with-claude/` chapter note — that connection doesn't hold; see [tool-choice-forcing.md](../tool-use-with-claude/tool-choice-forcing.md) for where that concept actually lives.)

On the boundary-case detection step in the Summary: the deterministic check (does the field literally appear in the source) shouldn't just be one option alongside a retry-count cutoff — it should run **first**, as a cheap fast path, with the retry loop as the fallback rather than the primary mechanism. Reasoning: a literal/keyword check on the source is fast and high-precision when it fires, so if a field genuinely isn't in the source text, that can be caught before burning any retries at all. But it can't be trusted alone — OCR noise, label variants (e.g. "P.O. #" vs "Purchase Order No."), and non-literal fields (something computed or derived, like a line-item sum, isn't "present" as a string to search for) all produce false negatives on a naive presence check. So the design should be: deterministic check first to short-circuit the obvious "not present" cases cheaply, retry-with-error-feedback as the safety net for everything the deterministic check can't resolve on its own — not a straight either/or between the two.

## Challenges

- Distinguishing "the model got it wrong" from "the information genuinely isn't there" is the crux of the whole pattern, and it's not always obvious from the extraction result alone which case you're in — it may need an explicit check (e.g. asking the model to also report "not found in document" as an allowed value, or a keyword search over the source) rather than inferring it from repeated failures.
- Setting a sensible retry cap (and what happens after it's exhausted) is a design decision with real cost trade-offs: too low and fixable errors get flagged as missing-data unnecessarily, too high and unfixable cases waste latency/cost before eventually landing in the same human-review queue anyway.
