## Summary

**Prompt engineering vs. prompt evaluation.** Prompt engineering is the set of
techniques used to write/edit a prompt so Claude understands what's being asked.
Prompt evaluation is automated testing of a prompt to get an objective metric of
how well it performs. This chapter is entirely about evaluation; prompt
engineering techniques come in the next chapter.

**Why bother with an eval pipeline.** Whenever you write a prompt you have three
paths: ship it after testing once or twice, tweak it against a few custom inputs,
or run it through a full evaluation pipeline. The first two are traps every
engineer falls into — testing too little before shipping to production. Running
an eval pipeline to get an objective score is the recommended path.

**The typical eval workflow, step by step:**
1. **Draft an initial prompt** — e.g. a simple system prompt like "Please answer
   the user's question," with user input interpolated in.
2. **Assemble an evaluation dataset** — sample inputs representing real-world
   use cases (a handful for learning, tens/hundreds/thousands in production).
   Can be built by hand or generated by Claude. The dataset is effectively the
   set of user queries that, combined with the system prompt, form the complete
   prompt sent to the API.
3. **Run each dataset record through the prompt** to get real Claude responses.
4. **Grade each response** — pair each question with its answer and feed both to
   a grader, typically producing a score from 1–10. Average all scores for one
   objective number describing overall prompt performance.
5. **Iterate** — tweak the prompt (e.g. add more detail/instructions), rerun the
   whole pipeline, and compare the new average score against the old one.

**Implementation, in a Jupyter notebook.** The course builds a custom eval
pipeline from scratch (rather than adopting a heavyweight off-the-shelf eval
framework) specifically to build intuition for how these pipelines work before
scaling up. Worked example: a prompt that asks Claude to solve AWS-related tasks
and return only Python, JSON, or a regular expression — no extra explanation.

- **Generating a dataset**: use a fast/cheap model (Haiku) to generate an array
  of `{task: ...}` JSON objects, using the same prefill + stop-sequence trick
  (assistant message primed with `` ``` json ``, stop sequence `` ``` ``) to get
  clean JSON back. Save the result to `dataset.json`.
- **Core pipeline functions**: `run_prompt` (merges a test case with the prompt
  template), `run_test_case` (runs the prompt, grades the output, returns the
  result), and a top-level runner that loops every test case, collects results,
  and averages the scores.

**Three types of graders:**
- **Code-based** — a snippet of code doing programmatic checks (length, banned
  words, syntax validation for JSON/code, readability scores). Cheap and fully
  deterministic.
- **Model-based** — feed the model's output into another API call whose system
  prompt asks it to rate quality/instruction-following/completeness, usually
  1–10. Very flexible but not fully objective (see Insights).
- **Human-based** — a person reviews outputs manually. Maximally flexible, but
  slow and tedious.

Whatever grader style is used, evaluation criteria must be defined upfront —
for the AWS example: output must be *only* Python/JSON/regex (no extra
explanation), and it must be syntactically valid for whichever format was
requested. Code-based validation for this used three helpers: `validate_json`,
`validate_python`, `validate_regex`.

## My Insights

- Model-based grading isn't as "objective" as the course frames it: if the
  grader is itself Claude, it inherits Claude's own biases/inconsistencies —
  objectivity depends entirely on how well the grader's system prompt is
  written, not on the mechanism itself.
- A "grader" demystified: it's just another server/process that calls the
  Claude API with a system prompt along the lines of "you are a prompt grader,
  rate this response 1–10 given the original prompt and Claude's answer."
  Once framed that way it stops feeling like a special mechanism.
- On the course's `run_test_case` design: it assumes the prompt is accessible
  system-wide (implicit/global), whereas Bruno would rather pass the prompt in
  as an explicit parameter — makes it straightforward to source it from a
  config file instead of hardcoding it. A design preference, not a correction
  of the course.
- Confirmed understanding that the "prompt" being evaluated here is really the
  **system prompt** — the eval dataset is the set of user queries that get
  combined with that system prompt to form what's actually sent to the API.
- See also: `system-prompt-api-vs-claude-code-sdk.md` for related system-prompt
  context outside this course's flow.
